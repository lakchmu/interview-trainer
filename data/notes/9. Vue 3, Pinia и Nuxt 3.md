## 1. Основы Vue 3: компоненты, шаблоны, директивы, реактивность и жизненный цикл

> [!tip]+ Коротко (что сказать вслух):
> Компонент Vue — это однофайловый `.vue` из трёх блоков: `<script setup>` с логикой, `<template>` с разметкой и `<style scoped>` со стилями. Шаблон — HTML с директивами (`v-if`, `v-for`, `v-model`, `:prop`, `@event`), на сборке он компилируется в render-функцию. Реактивность построена на Proxy: во время рендера Vue запоминает, какие реактивные значения компонент прочитал, и перерисовывает его, только когда изменились именно они. Главное отличие от React: код в `setup` выполняется один раз при создании компонента, а не на каждый рендер, поэтому нет массивов зависимостей и почти не нужна ручная мемоизация.

### Vue глазами React-разработчика

| React | Vue 3 | В чём разница |
| --- | --- | --- |
| `useState` | `ref`, `reactive` | значение меняют напрямую, сеттера нет |
| `useMemo` | `computed` | зависимости собираются сами |
| `useEffect` | `watch`, `watchEffect`, `onMounted` | массива зависимостей нет |
| `useRef` на DOM-узел | `ref` + атрибут `ref` в шаблоне | — |
| props | `defineProps` | props реактивны и только для чтения |
| колбэк-проп `onChange` | событие через `emit` | ребёнок сообщает, родитель решает |
| `children`, render props | слоты | именованные и со своими данными |
| Context | `provide` / `inject` | — |
| JSX | шаблон с директивами | шаблон анализируется компилятором |
| кастомный хук | composable | вызывается один раз, правил хуков нет |
| Redux Toolkit, Zustand | Pinia | состояние мутируют напрямую |
| Next.js | Nuxt | те же идеи: файловые маршруты, SSR |

### Однофайловый компонент

```vue
<script setup lang="ts">
import { ref, computed } from 'vue'

const props = defineProps<{ title: string }>()
const emit = defineEmits<{ close: [] }>()

const count = ref(0)
const double = computed(() => count.value * 2)
</script>

<template>
  <h2>{{ props.title }}</h2>
  <button @click="count++">{{ count }} × 2 = {{ double }}</button>
  <button @click="emit('close')">Закрыть</button>
</template>

<style scoped>
h2 { margin: 0; }
</style>
```

- Всё, что объявлено на верхнем уровне `<script setup>`, доступно в шаблоне.
- В скрипте к `ref` обращаются через `.value`, в шаблоне — без него: Vue разворачивает сам.
- `scoped` добавляет элементам компонента уникальный data-атрибут, и селекторы не утекают наружу.

### Директивы, которые нужно знать

| Директива | Сокращение | Что делает |
| --- | --- | --- |
| `v-if`, `v-else-if`, `v-else` | — | условный рендер: узла нет в DOM |
| `v-show` | — | переключает `display: none`, узел остаётся |
| `v-for` | — | список; каждому элементу нужен `:key` |
| `v-bind:href` | `:href` | привязывает атрибут или проп к выражению |
| `v-on:click` | `@click` | слушает событие; модификаторы `.prevent`, `.stop`, `.once`, `.enter` |
| `v-model` | — | двусторонняя связь поля и состояния |
| `v-slot:name` | `#name` | содержимое именованного слота |
| `v-html` | — | вставляет строку как HTML — источник XSS |

### v-if или v-show, и почему v-if не ставят рядом с v-for

| | `v-if` | `v-show` |
| --- | --- | --- |
| Что происходит | узел создаётся и удаляется | узел есть всегда, меняется `display` |
| Цена переключения | выше | почти нулевая |
| Цена первого рендера | ниже, если условие ложно | платится всегда |
| Когда брать | условие меняется редко | переключается часто: вкладки, тултипы |

На одном элементе `v-if` и `v-for` не совмещают: во Vue 3 у `v-if` приоритет выше, и переменной цикла он ещё не видит. Решения два — отфильтровать список в `computed` или вынести `v-for` на обёртку `<template>`:

```vue
<template v-for="user in users" :key="user.id">
  <li v-if="user.active">{{ user.name }}</li>
</template>
```

### Как работает реактивность

1. `reactive(obj)` возвращает Proxy над объектом. `ref(value)` — объект с геттером и сеттером на `.value`; если внутрь положили объект, он тоже становится реактивным.
2. Чтение свойства (get) вызывает **track**: Vue записывает, какой эффект сейчас выполняется и от чего он теперь зависит.
3. Запись (set) вызывает **trigger**: все эффекты, зависящие от этого свойства, ставятся на перезапуск.
4. Рендер компонента — тоже эффект. Поэтому изменение `count.value` перерисует только те компоненты, которые `count` читали.
5. Обновления DOM копятся и применяются одной пачкой в следующем «тике». Чтобы прочитать уже обновлённый DOM, ждут `await nextTick()`.

В React наоборот: компонент-функция вызывается заново целиком, а лишнюю работу отсекают `memo`, `useMemo`, `useCallback`. Во Vue точные зависимости известны системе, и эти приёмы почти не нужны.

### Props вниз, события вверх, слоты

```vue
<!-- Родитель -->
<UserCard :user="user" @select="onSelect">
  <template #footer="{ isOnline }">
    <span v-if="isOnline">в сети</span>
  </template>
</UserCard>
```

```vue
<!-- UserCard.vue -->
<script setup lang="ts">
defineProps<{ user: User }>()
const emit = defineEmits<{ select: [id: number] }>()
</script>

<template>
  <article @click="emit('select', user.id)">
    {{ user.name }}
    <slot name="footer" :is-online="user.online" />
  </article>
</template>
```

- Поток данных односторонний: проп менять нельзя, Vue выдаст предупреждение. Нужно изменить — отправляют событие родителю.
- Слот без имени — аналог `children`. Слот, который отдаёт данные наружу (`:is-online`), — аналог render props.

### Жизненный цикл

| Хук | Когда срабатывает | Ближайший аналог в React |
| --- | --- | --- |
| код в `<script setup>` | один раз при создании, DOM ещё нет | тело компонента, но без повторов |
| `onBeforeMount` | перед первой вставкой в DOM | — |
| `onMounted` | DOM вставлен, можно мерить и вешать слушатели | `useEffect(fn, [])` |
| `onBeforeUpdate` | данные изменились, DOM ещё старый | — |
| `onUpdated` | DOM обновлён | `useEffect` без массива |
| `onBeforeUnmount` | компонент ещё цел, пора отписываться | cleanup из `useEffect` |
| `onUnmounted` | компонент удалён | cleanup из `useEffect` |

- Порядок монтирования — изнутри наружу: `onMounted` ребёнка сработает раньше, чем у родителя.
- При серверном рендере `onMounted` и хуки обновления не вызываются: DOM на сервере нет.
- `onErrorCaptured` ловит ошибки потомков — аналог Error Boundary. `onActivated` и `onDeactivated` работают внутри `<KeepAlive>`.

> [!warning]- Подводные камни:
> - Забыть `.value` в скрипте. В шаблоне он не нужен, в скрипте без него получаешь объект-обёртку, а не значение.
> - Деструктурировать `reactive`-объект: `const { count } = state` даёт обычное число, связь с состоянием рвётся. Лечится `toRefs(state)`.
> - Ставить индекс массива в `:key` — та же ошибка, что и в React: при вставке и сортировке состояние строк перепутается.
> - Менять проп внутри ребёнка. Поток данных односторонний, нужно событие.
> - Читать DOM сразу после изменения состояния. Он обновится только в следующем тике — нужен `nextTick()`.
> - Вставлять пользовательский текст через `v-html`. Это прямая дорога к XSS.

### 💡 Что изменилось между Vue 2 и Vue 3

Готовый ответ на минуту — на случай, если в резюме обе версии и спросят про разницу.

| Что | Vue 2 | Vue 3 |
| --- | --- | --- |
| Реактивность | `Object.defineProperty`; новые свойства и запись по индексу массива не отслеживались, нужен был `$set` | `Proxy`; отслеживается всё |
| Логика компонента | Options API, переиспользование через миксины | Composition API и `<script setup>`, переиспользование через composables |
| Стор | Vuex с мутациями | Pinia, мутаций нет |
| Корень шаблона | ровно один элемент | несколько (фрагменты) |
| `v-model` на компоненте | проп `value` и событие `input`, один на компонент, плюс `.sync` | `modelValue` и `update:modelValue`, можно несколько, `.sync` убран |
| `v-if` рядом с `v-for` | приоритет у `v-for` | приоритет у `v-if` |
| Запуск приложения | `new Vue()` с глобальными настройками | `createApp()`, настройки на экземпляр |
| Убрано | — | фильтры, шина событий `$on` / `$off` |
| Nuxt | `asyncData`, файл `_id.vue` | `useAsyncData` и `useFetch`, файл `[id].vue` |

Первые три строки — главное: с них и начинать. Остальное называть, если попросят продолжить.

## 2. Composition API: как собрать компонент из ref, computed и watch

> [!tip]+ Коротко (что сказать вслух):
> Composition API — способ описывать логику компонента функциями: состояние — `ref` или `reactive`, производные значения — `computed`, побочные эффекты — `watch` и `watchEffect`, жизненный цикл — `onMounted` и остальные хуки. Логика группируется по смыслу, а не по опциям `data` / `methods` / `computed`, и выносится в composables — функции вида `useSomething`. Это аналог кастомных хуков, но без правил хуков: `setup` выполняется один раз, поэтому нет устаревших замыканий и массивов зависимостей — зависимости Vue собирает сам по фактическим чтениям.

### ref и reactive: что выбрать

| | `ref` | `reactive` |
| --- | --- | --- |
| Что принимает | любое значение | только объекты, массивы, Map, Set |
| Доступ в скрипте | через `.value` | напрямую |
| Заменить целиком | можно: `list.value = []` | нельзя: связь с шаблоном потеряется |
| Деструктуризация | ref остаётся ref | свойства теряют реактивность |
| Вернуть из composable | удобно | нужен `toRefs` |

```ts
const count = ref(0)
count.value++

const form = reactive({ email: '', agree: false })
form.email = 'a@b.ru'
```

Документация Vue советует брать `ref` по умолчанию: у него нет ловушек с заменой и деструктуризацией. `reactive` удобен для группы связанных полей, которую не будут ни заменять, ни разбирать.

### computed: кэш и правила

```ts
const items = ref<Item[]>([])
const total = computed(() => items.value.reduce((sum, i) => sum + i.price, 0))
```

- Значение кэшируется и пересчитывается, только когда изменилась хотя бы одна прочитанная зависимость. Метод в шаблоне, наоборот, выполняется на каждом рендере.
- Вычисление ленивое: пока `total` никто не читает, функция не вызывается.
- Геттер должен быть чистым: без запросов, без изменения других значений, без работы с DOM. Для побочных эффектов есть `watch`.
- Результат только для чтения. Нужна запись — передают объект с `get` и `set`.
- Массив зависимостей, как в `useMemo`, не пишут: забыть зависимость невозможно.

### watch и watchEffect

| | `watch(source, cb)` | `watchEffect(fn)` |
| --- | --- | --- |
| За чем следит | за явно указанным источником | за всем, что прочитано при выполнении |
| Первый запуск | не запускается, пока источник не изменится | сразу |
| Старое значение | есть: `(newValue, oldValue)` | нет |
| Когда брать | нужна реакция на конкретное изменение | надо синхронизировать что-то с состоянием |

Опции `watch`: `immediate: true` — выполнить сразу; `deep: true` — следить за вложенными свойствами; `flush: 'post'` — запускать после обновления DOM (по умолчанию колбэк срабатывает до него).

```ts
watch(userId, async (id, _old, onCleanup) => {
  const controller = new AbortController()
  onCleanup(() => controller.abort()) // сработает перед следующим запуском
  user.value = await $fetch(`/api/users/${id}`, { signal: controller.signal })
})
```

`onCleanup` решает ту же задачу, что функция очистки в `useEffect`: отменяет устаревший запрос.

### Что передавать в watch первым аргументом

| Источник | Пример | Работает? |
| --- | --- | --- |
| ref | `watch(count, cb)` | да |
| геттер | `watch(() => props.id, cb)` | да |
| reactive-объект | `watch(state, cb)` | да, следит глубоко |
| массив источников | `watch([a, () => b.value], cb)` | да |
| значение свойства | `watch(props.id, cb)` | **нет** |

Последняя строка — самая частая ошибка: в `watch` уходит не источник, а уже прочитанное число, и следить не за чем. Свойство `reactive`-объекта или пропа всегда оборачивают в геттер.

Вторая ловушка: геттер, который возвращает объект (`() => state.user`), срабатывает только при замене объекта целиком. Чтобы ловить изменения внутри, добавляют `deep: true`.

### Composables — аналог кастомных хуков

```ts
// composables/useCounter.ts
export function useCounter(initial = 0) {
  const count = ref(initial)
  const double = computed(() => count.value * 2)
  const inc = () => count.value++
  return { count, double, inc }
}
```

```ts
const { count, double, inc } = useCounter(10) // деструктурировать можно: это ref
```

| | Хук React | Composable Vue |
| --- | --- | --- |
| Сколько раз вызывается | на каждый рендер | один раз в `setup` |
| Порядок и условия вызова | строго на верхнем уровне | ограничений по порядку нет |
| Массивы зависимостей | нужны | не нужны |
| Устаревшие замыкания | бывают | нет: читается актуальный `.value` |

Ограничение одно: хуки жизненного цикла и наблюдатели внутри composable должны регистрироваться синхронно, пока выполняется `setup` компонента.

### Макросы script setup

| Макрос | Зачем |
| --- | --- |
| `defineProps<{ … }>()` | объявить входные параметры |
| `defineEmits<{ … }>()` | объявить события компонента |
| `defineModel()` | поддержать `v-model` на компоненте (Vue 3.4+) |
| `defineExpose({ … })` | открыть родителю методы через ref на компонент |
| `defineOptions({ … })` | задать опции вроде `inheritAttrs` |

Макросы не импортируют: это подсказки компилятору, в рантайме таких функций нет. Ссылка на DOM-узел — `const input = ref<HTMLInputElement | null>(null)` плюс `ref="input"` в шаблоне; значение появится к `onMounted`.

### Composition API и Options API

| | Options API | Composition API |
| --- | --- | --- |
| Как устроен компонент | объект с `data`, `computed`, `methods`, `watch` | функции внутри `setup` |
| Где лежит логика одной фичи | размазана по опциям | рядом, одним куском |
| Переиспользование | миксины: конфликты имён, неясный источник | composables: явный импорт |
| TypeScript | типы выводятся с трудом, везде `this` | обычные переменные и функции |

Оба стиля поддерживаются, и Options API никуда не исчезает. Но в требованиях вакансий обычно назван именно Composition API, и новый код на Vue 3 пишут на нём.

> [!warning]- Подводные камни:
> - `watch` не срабатывает при монтировании. Нужен первый запуск — `immediate: true` или `watchEffect`.
> - `watchEffect` отслеживает только то, что прочитано синхронно. Всё, что читается после первого `await`, в зависимости не попадёт.
> - Побочные эффекты и запросы внутри `computed`. Он должен только вычислять.
> - Замена `reactive`-объекта целиком: `state = reactive({ … })` рвёт связь с шаблоном. Либо менять поля, либо держать объект в `ref`.
> - Регистрация `onMounted` или `watch` после `await` в обычной async-функции: компонент уже не «текущий», и хук молча не привяжется.
> - Передача `props.id` в composable. Туда уйдёт число, а не источник — передавайте геттер или `toRef(props, 'id')`.

## 3. State management: как устроена Pinia и чем она отличается от знакомых сторов

> [!tip]+ Коротко (что сказать вслух):
> Pinia — официальный стор для Vue 3, сменивший Vuex. Стор объявляют через `defineStore(id, …)`, внутри три вещи: state — данные, getters — вычисляемые значения стора (те же `computed`), actions — методы, в том числе асинхронные. Мутаций, как во Vuex, нет: состояние меняют напрямую или внутри action, а Proxy сам отследит изменение. Стор создаётся лениво при первом вызове `useXStore()`, типы выводятся без ручных описаний, история изменений видна в Vue DevTools.

### Два синтаксиса стора

```ts
// Option store — похоже на Options API
export const useCartStore = defineStore('cart', {
  state: () => ({ items: [] as Item[] }),
  getters: {
    total: (state) => state.items.reduce((sum, i) => sum + i.price, 0),
  },
  actions: {
    add(item: Item) {
      this.items.push(item)
    },
  },
})
```

```ts
// Setup store — тот же Composition API
export const useCartStore = defineStore('cart', () => {
  const items = ref<Item[]>([])
  const total = computed(() => items.value.reduce((sum, i) => sum + i.price, 0))
  function add(item: Item) {
    items.value.push(item)
  }
  return { items, total, add }
})
```

Соответствие прямое: `ref` — это state, `computed` — getter, функция — action. Setup-стор гибче (внутри можно использовать composables и `watch`), но из него нужно вернуть всё, что должно быть видно снаружи.

### Как читать стор в компоненте

```ts
const cart = useCartStore()

const { items, total } = storeToRefs(cart) // state и getters — через storeToRefs
const { add } = cart                       // actions — обычной деструктуризацией
```

Стор — это `reactive`-объект, поэтому прямая деструктуризация `const { items } = cart` даёт снимок значения, который больше не обновляется. `storeToRefs` превращает каждое поле state и каждый getter в `ref`, сохраняя связь. Actions — обычные функции, им `storeToRefs` не нужен.

Без деструктуризации тоже можно: `cart.items` и `cart.total` в шаблоне остаются реактивными.

### Как менять состояние

| Способ | Пример | Когда |
| --- | --- | --- |
| напрямую | `cart.items.push(item)` | простое точечное изменение |
| `$patch` объектом | `cart.$patch({ coupon: 'A1' })` | несколько полей одной записью в DevTools |
| `$patch` функцией | `cart.$patch((s) => s.items.push(item))` | изменения массивов и вложенных структур |
| action | `cart.add(item)` | есть логика, запрос или несколько шагов |
| `$reset()` | `cart.$reset()` | вернуть начальное состояние |

- `$reset()` из коробки работает только в option-сторах: там есть функция `state`, которую можно вызвать заново. В setup-сторе сброс пишут сами.
- `cart.$subscribe(cb)` — подписка на изменения состояния, например для записи в `localStorage`. `cart.$onAction(cb)` — на вызовы actions.

### Pinia рядом с Redux Toolkit и Zustand

| Что | Redux Toolkit | Zustand | Pinia |
| --- | --- | --- | --- |
| Единица состояния | slice в общем сторе | отдельный стор-хук | отдельный стор |
| Изменение | `dispatch(action)`, редьюсер | `set(…)` | прямая мутация или action |
| Иммутабельность | нужна (Immer под капотом) | нужна | не нужна: изменения ловит Proxy |
| Производные данные | селекторы, `createSelector` | селекторы | getters с кэшем `computed` |
| Асинхронность | thunk, RTK Query | обычные функции | обычные async-actions |
| Подписка компонента | `useSelector` с селектором | хук с селектором | автоматически, по фактическим чтениям |
| Подключение | `<Provider store>` | не нужно | `app.use(createPinia())` |

Главное, что стоит сказать вслух: в Pinia не выбирают, на что подписаться, — компонент перерисуется ровно от тех полей, которые прочитал.

### Что класть в стор, а что нет

| В стор | Не в стор |
| --- | --- |
| пользователь, сессия, права | открыт ли выпадающий список |
| корзина, избранное | текст в поле до отправки формы |
| настройки и язык интерфейса | всё, что нужно одному компоненту |
| данные, общие для нескольких страниц | производные значения — им место в getters |

Стор — общая память приложения, а не замена локальному состоянию. Признак лишнего: поле читает и пишет один-единственный компонент.

### Pinia и серверный рендеринг

- В Nuxt Pinia подключают модулем `@pinia/nuxt`. Он создаёт экземпляр Pinia на каждый запрос и сам переносит состояние с сервера на клиент.
- Почему «на каждый запрос»: сервер один на всех пользователей. Состояние в переменной уровня модуля утекло бы от одного посетителя к другому.
- Состояние стора сериализуется в HTML и на клиенте восстанавливается при гидратации. Значит, в state кладут только то, что переживает сериализацию.
- `useCartStore()` вызывают внутри `setup`, action или middleware — там, где есть активный экземпляр Pinia. Вызов на верхнем уровне модуля падает с ошибкой про отсутствие активной Pinia.

> [!warning]- Подводные камни:
> - Деструктурировать стор без `storeToRefs` — значения перестают обновляться.
> - Вызвать `useStore()` на верхнем уровне файла, до `app.use(pinia)`.
> - Рассчитывать на `$reset()` в setup-сторе — его там нет.
> - Держать в сторе локальное состояние интерфейса: стор разрастается, компоненты связываются без причины.
> - Дублировать в state то, что вычисляется из других полей. Для этого есть getters.
> - Два стора, которые читают друг друга прямо при создании, дают бесконечный цикл. Обращаться к соседу нужно внутри action или getter.

## 4. Формы и валидация: как работает v-model и где проверять данные

> [!tip]+ Коротко (что сказать вслух):
> Поле связывают с состоянием директивой `v-model` — это сахар над «привязать значение и слушать событие». На нативных элементах она сама выбирает пару: `value` и `input` для текста, `checked` и `change` для чекбокса. На своём компоненте это проп `modelValue` и событие `update:modelValue`; с Vue 3.4 их объявляет макрос `defineModel`. Форму отправляют через `@submit.prevent`. Простую валидацию пишут руками на `computed`, сложную отдают библиотеке — VeeValidate со схемой Zod или Yup, либо Vuelidate. Проверка на клиенте — ради удобства человека; сервер всё равно проверяет заново.

### v-model на нативных элементах

| Элемент | Что связывается | Событие |
| --- | --- | --- |
| `<input type="text">`, `<textarea>` | `value` | `input` |
| `<input type="checkbox">` | `checked` — булево значение или массив выбранных | `change` |
| `<input type="radio">` | `checked` — значение выбранной кнопки | `change` |
| `<select>` | `value`; с `multiple` — массив | `change` |

| Модификатор | Что меняет |
| --- | --- |
| `.lazy` | обновлять по `change` (после потери фокуса), а не на каждый символ |
| `.number` | приводить ввод к числу |
| `.trim` | обрезать пробелы по краям |

### Во что разворачивается v-model

```vue
<input v-model="text" />
<!-- то же самое, что -->
<input :value="text" @input="text = $event.target.value" />
```

```vue
<SearchField v-model="query" />
<!-- то же самое, что -->
<SearchField :model-value="query" @update:model-value="query = $event" />
```

У компонента может быть несколько связей с именами: `v-model:title="title"` — это проп `title` и событие `update:title`.

В React то же самое пишут руками: `value` плюс `onChange` — управляемое поле. `v-model` — готовая запись этого паттерна, а не отдельный механизм.

### v-model на своём компоненте

```vue
<!-- SearchField.vue, Vue 3.4+ -->
<script setup lang="ts">
const model = defineModel<string>({ default: '' })
</script>

<template>
  <input v-model="model" type="search" />
</template>
```

`defineModel` возвращает `ref`: чтение берёт значение из пропа, запись отправляет событие `update:modelValue` родителю. До версии 3.4 то же писали вручную:

```ts
const props = defineProps<{ modelValue: string }>()
const emit = defineEmits<{ 'update:modelValue': [value: string] }>()
// в шаблоне: :value="props.modelValue" @input="emit('update:modelValue', $event.target.value)"
```

Менять проп напрямую нельзя и здесь: данными владеет родитель, ребёнок только сообщает о желании их изменить.

### Валидация вручную

```vue
<script setup lang="ts">
const form = reactive({ email: '', password: '' })
const touched = reactive({ email: false, password: false })

const errors = computed(() => ({
  email: /^\S+@\S+\.\S+$/.test(form.email) ? '' : 'Введите почту',
  password: form.password.length >= 8 ? '' : 'Минимум 8 символов',
}))
const valid = computed(() => Object.values(errors.value).every((e) => !e))

async function submit() {
  touched.email = touched.password = true
  if (!valid.value) return
  await $fetch('/api/login', { method: 'POST', body: form })
}
</script>

<template>
  <form novalidate @submit.prevent="submit">
    <input v-model.trim="form.email" type="email" @blur="touched.email = true" />
    <p v-if="touched.email && errors.email">{{ errors.email }}</p>
    <button :disabled="!valid">Войти</button>
  </form>
</template>
```

Ошибки — `computed` от значений формы, отдельно их не хранят. `touched` нужен, чтобы не ругаться на поле, к которому человек ещё не прикасался.

### Библиотеки валидации

| Инструмент | Идея | Когда брать |
| --- | --- | --- |
| нативная валидация HTML | атрибуты `required`, `pattern`, `min`, `type="email"` | простые формы, быстрый старт |
| VeeValidate | состояние формы и полей; правила — функции или схема | большие формы, асинхронные проверки |
| Vuelidate | правила описываются рядом с моделью данных | валидация модели, а не разметки |
| Zod, Yup | схема данных, одна для формы и для ответа API | вместе с VeeValidate; типы выводятся из схемы |

```ts
const schema = toTypedSchema(z.object({ email: z.string().email(), age: z.number().min(18) }))
const { handleSubmit, errors, defineField } = useForm({ validationSchema: schema })
const [email, emailAttrs] = defineField('email')
const onSubmit = handleSubmit((values) => $fetch('/api/signup', { method: 'POST', body: values }))
```

### Что проверить в любой форме

| Вопрос | Обычный ответ |
| --- | --- |
| Когда показывать ошибку | после ухода с поля или после попытки отправки, не на первый же символ |
| Что с ошибками сервера | раскладывать по полям тем же механизмом, что и клиентские |
| Двойная отправка | блокировать кнопку, пока запрос в полёте |
| Доступность | `<label>` у каждого поля, `aria-invalid`, текст ошибки связан через `aria-describedby` |
| Нативные подсказки браузера | отключить через `novalidate`, если рисуете свои |
| Кому верить | серверу: клиентскую проверку обходят одним запросом |

> [!warning]- Подводные камни:
> - `.number` возвращает строку, если ввод не разбирается как число. Пустое поле даёт `''`, а не `0`.
> - Во время набора через IME (китайский, японский ввод) `v-model` не обновляется до конца композиции.
> - Несколько чекбоксов на один массив требуют атрибут `value` у каждого, иначе все переключаются разом.
> - Менять `modelValue` внутри компонента вместо отправки события.
> - Хранить ошибки отдельным состоянием и забывать их пересчитать. Ошибки — производные данные, им место в `computed`.
> - Считать клиентскую валидацию защитой. Это удобство, а не безопасность.

## 5. Основы Nuxt 3: структура проекта, страницы и компоненты

> [!tip]+ Коротко (что сказать вслух):
> Nuxt — фреймворк над Vue, как Next над React: файловая маршрутизация, серверный рендеринг из коробки, автоимпорты и собственный сервер на движке Nitro. Многое держится на соглашениях о папках: файл в `pages/` становится маршрутом, компонент из `components/` и функция из `composables/` доступны без импорта. По умолчанию рендеринг универсальный: первый запрос сервер превращает в готовый HTML, затем на клиенте проходит гидратация, и дальше приложение работает как SPA. Режим можно менять для всего сайта или для отдельных маршрутов.

### Структура проекта

| Папка или файл | Что там лежит | Что делает Nuxt |
| --- | --- | --- |
| `pages/` | страницы | строит маршруты по именам файлов |
| `components/` | компоненты | импортирует автоматически |
| `composables/` | функции `useSomething` | импортирует автоматически |
| `utils/` | вспомогательные функции | импортирует автоматически |
| `layouts/` | каркасы страниц: шапка, подвал | оборачивает страницу выбранным layout |
| `middleware/` | проверки перед переходом | запускает перед маршрутом |
| `plugins/` | код, выполняемый при старте приложения | подключает сам |
| `server/` | `api/`, `routes/`, `middleware/` | поднимает серверные обработчики Nitro |
| `public/` | файлы, отдаваемые как есть | раздаёт от корня сайта |
| `assets/` | стили, шрифты, картинки для сборки | пропускает через сборщик |
| `app.vue` | корневой компонент | точка входа |
| `nuxt.config.ts` | настройки, модули, режимы рендеринга | — |

Сторы по соглашению кладут в `stores/`. В Nuxt 4 папки приложения переехали внутрь `app/`, сами соглашения остались теми же.

### app.vue, layout и страница

```vue
<!-- app.vue -->
<template>
  <NuxtLayout>
    <NuxtPage />
  </NuxtLayout>
</template>
```

```vue
<!-- layouts/default.vue -->
<template>
  <AppHeader />
  <main><slot /></main>
</template>
```

```vue
<!-- pages/admin.vue -->
<script setup lang="ts">
definePageMeta({ layout: 'admin' })
</script>
```

- `<NuxtPage />` — место, куда подставляется текущая страница из `pages/`.
- `<NuxtLayout>` оборачивает её каркасом. Без указаний берётся `layouts/default.vue`, другой выбирают через `definePageMeta`.
- В layout страница попадает в `<slot />`.

### Автоимпорты

| Что доступно без импорта | Откуда |
| --- | --- |
| `ref`, `computed`, `watch`, `onMounted` | Vue |
| `useFetch`, `useRoute`, `navigateTo`, `useState` | Nuxt |
| компоненты | `components/` |
| свои функции | `composables/`, `utils/` |

Имя компонента складывается из пути: `components/base/Button.vue` становится `<BaseButton>`.

- Плюс: меньше шаблонного кода, а в сборку попадает только использованное.
- Минус: по файлу не видно, откуда взялась функция. Спасают типы, которые Nuxt генерирует в `.nuxt/`, и переход к определению в редакторе.
- Импортировать явно тоже можно — из псевдонима `#imports`.

### Режимы рендеринга

| Режим | Как включить | Где собирается HTML | Когда подходит |
| --- | --- | --- | --- |
| универсальный (SSR) | по умолчанию | на сервере при запросе | каталог, карточка товара, всё для поисковиков |
| только клиент (SPA) | `ssr: false` | в браузере | личный кабинет, админка |
| статическая генерация (SSG) | `nuxt generate` | на этапе сборки | документация, лендинги |
| гибридный | `routeRules` в конфиге | свой способ у каждого маршрута | большой сайт с разными разделами |

```ts
export default defineNuxtConfig({
  routeRules: {
    '/': { prerender: true },      // собрать при сборке
    '/catalog/**': { swr: 3600 },  // кэшировать на час, обновлять в фоне
    '/account/**': { ssr: false }, // только на клиенте
  },
})
```

### Гидратация и код, который выполняется дважды

Код в `<script setup>` страницы выполняется и на сервере, и в браузере. Отсюда три правила.

1. **Браузерных API на сервере нет.** `window`, `document`, `localStorage` используют внутри `onMounted`, под условием `import.meta.client` или в компоненте, обёрнутом в `<ClientOnly>`.
2. **Разметка должна совпасть.** Если сервер и клиент отрисовали разное, получится hydration mismatch: предупреждение в консоли и перерисовка куска страницы. Типичные причины — `Date.now()`, `Math.random()`, ветвление по `localStorage` или ширине окна.
3. **Общее состояние — через `useState` или Pinia.** `const user = ref()` на верхнем уровне модуля живёт на сервере один на всех посетителей и утекает между запросами. `useState('user', () => null)` создаётся на каждый запрос и переносится на клиент.

### Серверная часть: server/api

```ts
// server/api/products/[id].get.ts
export default defineEventHandler(async (event) => {
  const id = getRouterParam(event, 'id')
  const product = await db.products.find(id)
  if (!product) throw createError({ statusCode: 404, statusMessage: 'Товар не найден' })
  return product // объект сам превратится в JSON
})
```

- Путь файла задаёт адрес: `/api/products/:id`. Суффикс `.get` ограничивает метод.
- Обработчик выполняется только на сервере: здесь можно держать секреты и ходить в базу.
- Вызов `$fetch('/api/products/1')` во время серверного рендера не делает HTTP-запрос, а вызывает обработчик напрямую.
- Секреты и адреса берут из `runtimeConfig`: ключи верхнего уровня видны только серверу, раздел `public` попадает и в браузер.

### Nuxt рядом с Next

| Задача | Next.js | Nuxt 3 |
| --- | --- | --- |
| маршруты из файлов | `app/` или `pages/` | `pages/` |
| динамический сегмент | `[id]` | `[id]` |
| каркас страниц | `layout.tsx` | `layouts/` и `<NuxtLayout>` |
| ссылка без перезагрузки | `<Link>` | `<NuxtLink>` |
| данные для страницы | серверные компоненты, `fetch` | `useFetch`, `useAsyncData` |
| серверные обработчики | Route Handlers | `server/api/` |
| проверка перед переходом | `middleware.ts` | `middleware/` и `server/middleware/` |
| переменные окружения | `process.env`, префикс `NEXT_PUBLIC_` | `runtimeConfig` и его раздел `public` |

> [!warning]- Подводные камни:
> - Состояние в переменной модуля — на сервере оно общее для всех посетителей.
> - `window` или `localStorage` на верхнем уровне `setup` — на сервере это ошибка.
> - Разная разметка на сервере и клиенте: время, случайные числа, данные из браузерного хранилища.
> - Секрет в `runtimeConfig.public` — он уедет в браузер.
> - Путать `middleware/` (перед переходом по маршруту) и `server/middleware/` (на каждый запрос к серверу).
> - Ждать в `onMounted` данные для первой отрисовки: на сервере этот хук не вызывается, и в HTML их не окажется.

## 6. Маршрутизация в Nuxt 3: файловые и динамические маршруты

> [!tip]+ Коротко (что сказать вслух):
> Маршруты строятся из файлов в `pages/`, под капотом работает Vue Router. Квадратные скобки — динамический сегмент: `pages/products/[id].vue` даёт `/products/:id`, параметр читают через `useRoute().params.id`. `[...slug].vue` ловит хвост пути любой длины, двойные скобки `[[lang]]` делают сегмент необязательным. Вложенные маршруты — это файл-родитель с `<NuxtPage />` внутри плюс одноимённая папка с дочерними страницами. Переходят через `<NuxtLink>` и `navigateTo()`, проверки перед входом пишут в route middleware.

### Файл → маршрут

| Файл | Адрес | Что в `route.params` |
| --- | --- | --- |
| `pages/index.vue` | `/` | — |
| `pages/about.vue` | `/about` | — |
| `pages/products/index.vue` | `/products` | — |
| `pages/products/[id].vue` | `/products/42` | `{ id: '42' }` |
| `pages/users-[group]/[id].vue` | `/users-admins/7` | `{ group: 'admins', id: '7' }` |
| `pages/[...slug].vue` | `/a/b/c` | `{ slug: ['a', 'b', 'c'] }` |
| `pages/[[lang]]/index.vue` | `/` и `/en` | `{ lang: '' }` или `{ lang: 'en' }` |

Имя маршрута складывается из пути: у `pages/products/[id].vue` это `products-id`.

### Чтение параметров

```vue
<script setup lang="ts">
const route = useRoute()

const id = computed(() => Number(route.params.id)) // параметры — всегда строки
const page = computed(() => Number(route.query.page ?? 1))
</script>
```

- `route.params` — сегменты пути, `route.query` — то, что после `?`.
- Объект `route` реактивный. Значение из него берут через `computed` или геттер — не копируют в обычную переменную.
- Проверить параметр до рендера можно в `definePageMeta`:

```ts
definePageMeta({
  validate: (route) => /^\d+$/.test(String(route.params.id)), // false → страница 404
})
```

### Что происходит при смене параметра

Переход с `/products/1` на `/products/2` ведёт на тот же файл страницы.

| Где | Поведение |
| --- | --- |
| чистый Vue Router | компонент переиспользуется: `setup` и `onMounted` повторно не выполняются, за параметром нужно следить через `watch(() => route.params.id, …)` |
| Nuxt | ключ страницы по умолчанию включает значения параметров, поэтому страница создаётся заново |

Надёжный способ, который работает в обоих случаях, — отдать параметр в загрузку данных реактивно:

```ts
const { data: product } = await useFetch(() => `/api/products/${route.params.id}`)
```

Поведение ключа меняют через `definePageMeta({ key: (route) => route.fullPath })`.

### Навигация: NuxtLink и navigateTo

```vue
<NuxtLink to="/products/42">Товар</NuxtLink>
<NuxtLink :to="{ name: 'products-id', params: { id: 42 }, query: { tab: 'reviews' } }">Отзывы</NuxtLink>
```

```ts
await navigateTo('/login')
await navigateTo({ path: '/search', query: { q: text.value } })
await navigateTo('/cart', { replace: true })                // без записи в историю
await navigateTo('https://ozon.ru', { external: true })     // внешний адрес
```

- `<NuxtLink>` переключает страницу без перезагрузки и заранее подгружает код страницы, когда ссылка появляется в области видимости.
- `navigateTo` работает и на сервере: во время серверного рендера он превращается в HTTP-редирект.
- Обычный `<a href>` на внутренний адрес перезагрузит приложение целиком и сбросит состояние.

### Вложенные маршруты

```text
pages/
  account.vue          ← родитель: общая шапка раздела и <NuxtPage />
  account/
    index.vue          → /account
    orders.vue         → /account/orders
    orders-[id].vue    → /account/orders-15
```

```vue
<!-- pages/account.vue -->
<template>
  <AccountTabs />
  <NuxtPage />
</template>
```

Файл и папка с одинаковым именем образуют пару «родитель — дети». Дочерняя страница рисуется на месте `<NuxtPage />` родителя; при переходе между детьми родитель не пересоздаётся. Если `<NuxtPage />` в родителе забыть, дочерние страницы не появятся вовсе.

### Route middleware

```ts
// middleware/auth.ts
export default defineNuxtRouteMiddleware((to, from) => {
  const user = useState('user')
  if (!user.value) return navigateTo({ path: '/login', query: { back: to.fullPath } })
})
```

```ts
definePageMeta({ middleware: 'auth' }) // подключить на странице
```

| Что вернуть | Что произойдёт |
| --- | --- |
| ничего | переход продолжается |
| `navigateTo(…)` | редирект |
| `abortNavigation()` | переход отменён |

- Файл с суффиксом `.global.ts` выполняется перед каждым переходом без подключения.
- При первом заходе на сайт middleware отрабатывает на сервере, а потом ещё раз на клиенте при гидратации.
- Это не то же самое, что `server/middleware/`: тот запускается на каждый запрос к серверу, включая запросы к API.

### Страница ошибки и 404

```ts
const { data: product } = await useFetch(`/api/products/${route.params.id}`)
if (!product.value) {
  throw createError({ statusCode: 404, statusMessage: 'Товар не найден', fatal: true })
}
```

- Файл `error.vue` в корне проекта — страница для любых фатальных ошибок. Объект ошибки приходит в неё пропом `error`.
- `fatal: true` нужен, чтобы ошибка, брошенная на клиенте, тоже показала полноэкранную страницу.
- `clearError({ redirect: '/' })` сбрасывает ошибку и уводит на рабочую страницу.
- Несуществующий адрес ловит либо встроенная 404, либо свой `pages/[...slug].vue`.

> [!warning]- Подводные камни:
> - Параметры маршрута — строки. `route.params.id === 42` всегда ложно.
> - У catch-all сегмента значение — массив, а не строка.
> - Забытый `<NuxtPage />` в родительской странице: дочерние маршруты есть, а на экране пусто.
> - `<a href>` вместо `<NuxtLink>` — полная перезагрузка.
> - `definePageMeta` — макрос компилятора: внутри нельзя ссылаться на переменные компонента.
> - Копировать `route.params.id` в константу при создании и ждать, что она обновится.

## 7. Работа с API: $fetch, useFetch и useAsyncData для асинхронных данных

> [!tip]+ Коротко (что сказать вслух):
> В Nuxt 3 три инструмента. `$fetch` — обёртка над fetch: сама разбирает JSON и бросает ошибку на ответах 4xx и 5xx; годится для действий по событию — отправить форму, нажать кнопку. `useFetch(url)` и `useAsyncData(key, fn)` — для данных, которые нужны при отрисовке страницы: запрос выполняется на сервере, результат кладётся в HTML и при гидратации повторно не запрашивается. `useFetch` — это сокращённая запись `useAsyncData` плюс `$fetch`. В списках тем к интервью до сих пор встречается слово «asyncData» — так назывался метод компонента в Nuxt 2; в Nuxt 3 его место заняли эти composables.

### Три инструмента

| | `$fetch` | `useFetch` | `useAsyncData` |
| --- | --- | --- | --- |
| Что это | функция запроса | composable | composable |
| Где вызывать | где угодно | в `setup` | в `setup` |
| Перенос результата с сервера на клиент | нет | да | да |
| Что возвращает | промис с данными | `data`, `status`, `error`, `refresh` | то же самое |
| Типичное применение | отправка формы, клик | один запрос по адресу | своя логика, несколько запросов, сторонний SDK |

### Почему в setup нельзя просто вызвать $fetch

```ts
// Плохо: запрос уйдёт дважды
const products = await $fetch('/api/products')
```

1. Сервер выполняет `setup`, делает запрос и рендерит HTML.
2. Браузер получает HTML и запускает гидратацию — `setup` выполняется второй раз.
3. Результат первого запроса никуда не сохранён, поэтому запрос уходит снова.

`useFetch` и `useAsyncData` кладут ответ в payload — блок данных внутри HTML. На клиенте composable сначала смотрит туда и, найдя данные по ключу, в сеть не идёт. Бонусом исчезает расхождение разметки: клиент рисует из тех же данных, что и сервер.

### useFetch: что возвращает и что принимает

```ts
const page = ref(1)

const { data, status, error, refresh } = await useFetch('/api/products', {
  query: { page },                 // ref: изменится — запрос повторится
  transform: (res) => res.items,   // привести ответ к нужному виду
  default: () => [],               // значение, пока данных нет
})
```

| Поле | Что в нём |
| --- | --- |
| `data` | `ref` с ответом; до загрузки — значение из `default` или пусто |
| `status` | `'idle'`, `'pending'`, `'success'` или `'error'` |
| `error` | `ref` с ошибкой или пусто |
| `refresh()` | повторить запрос вручную |

Частые опции: `method`, `body`, `headers`, `query`, `key`, `lazy`, `server`, `immediate`, `watch`, `pick`. Ключ для кэша `useFetch` выводит сам из адреса и опций.

### useAsyncData: когда нужен именно он

```ts
const route = useRoute()

const { data } = await useAsyncData(
  `product-${route.params.id}`, // ключ: по нему данные находятся в payload
  async () => {
    const [product, reviews] = await Promise.all([
      $fetch(`/api/products/${route.params.id}`),
      $fetch(`/api/products/${route.params.id}/reviews`),
    ])
    return { product, reviews }
  },
)
```

| Ситуация | Что брать |
| --- | --- |
| один запрос по адресу | `useFetch` |
| несколько запросов, которые нужны вместе | `useAsyncData` |
| данные приходят не через `$fetch`: SDK, GraphQL-клиент | `useAsyncData` |
| нужен свой ключ, чтобы читать те же данные в другом компоненте | `useAsyncData` |

Ключ должен быть уникален для набора данных. Одинаковый ключ в двух местах означает одни и те же данные на двоих — это и возможность, и источник путаницы.

### Реактивные параметры и повторный запрос

| Способ | Пример | Когда запрос повторится |
| --- | --- | --- |
| адрес-геттер | `useFetch(() => '/api/products/' + id.value)` | при изменении `id` |
| ref в `query` | `useFetch('/api/products', { query: { page } })` | при изменении `page` |
| опция `watch` | `useAsyncData(key, fn, { watch: [id] })` | при изменении любого источника |
| вручную | `refresh()` | по вызову |
| отложенный старт | `{ immediate: false }` и затем `execute()` | только по вызову |

Строка-шаблон, собранная один раз (`` `/api/products/${id.value}` ``), не реактивна: в `useFetch` уйдёт готовая строка. Нужен именно геттер.

### lazy: блокировать навигацию или нет

| | `await useFetch(…)` | `useLazyFetch(…)` или `lazy: true` |
| --- | --- | --- |
| Переход на клиенте | ждёт ответа, потом показывает страницу | страница открывается сразу |
| Что видит человек | старую страницу до конца загрузки | новую страницу с состоянием загрузки |
| Что обязательно в шаблоне | — | ветка для `status === 'pending'` |

```vue
<p v-if="status === 'pending'">Загружаем…</p>
<p v-else-if="error">Не получилось: {{ error.message }}</p>
<ProductList v-else :items="data" />
```

Опция `server: false` отключает запрос на сервере совсем: данные загрузятся только в браузере после гидратации. Так поступают с тем, что не нужно поисковикам и зависит от браузера.

### $fetch в обработчике: отправка формы

```ts
const pending = ref(false)
const formError = ref('')

async function submit() {
  pending.value = true
  formError.value = ''
  try {
    await $fetch('/api/orders', { method: 'POST', body: form })
    await refreshNuxtData('orders') // обновить список, загруженный через useAsyncData
  } catch (e) {
    formError.value = e.data?.message ?? 'Не удалось оформить заказ'
  } finally {
    pending.value = false
  }
}
```

- `$fetch` сам ставит `Content-Type`, сериализует `body` в JSON и разбирает ответ.
- На 4xx и 5xx он бросает ошибку — в отличие от нативного `fetch`, где надо проверять `response.ok`. В ошибке есть `statusCode` и разобранное тело `data`.
- `useFetch` внутри обработчика клика не вызывают: это composable, его место — `setup`.

### То же самое в мире React

| Задача | React | Nuxt 3 |
| --- | --- | --- |
| загрузить данные для страницы | серверный компонент, `getServerSideProps` | `await useFetch(…)` |
| загрузить на клиенте с состоянием загрузки | TanStack Query, `useEffect` + `fetch` | `useLazyFetch`, `server: false` |
| ключ кэша | `queryKey` | `key` |
| повторить запрос | `refetch`, `invalidateQueries` | `refresh`, `refreshNuxtData` |
| отправить изменение | `useMutation` | `$fetch` в обработчике |

Важная оговорка: `useAsyncData` — не полная замена TanStack Query. Он решает перенос данных с сервера и дедупликацию по ключу, но сам не обновляет данные по фокусу окна и не ведёт учёт устаревания.

> [!warning]- Подводные камни:
> - `$fetch` в `setup` страницы с SSR — двойной запрос и возможное расхождение разметки.
> - `useFetch` в обработчике события. Там нужен `$fetch`.
> - Одинаковый ключ у разных данных — компоненты начнут показывать чужой ответ.
> - `data` — это `ref`, и до загрузки он пуст. В шаблоне нужна ветка на «ещё нет данных», в скрипте — `data.value?.items`.
> - Адрес собран строкой один раз — смена параметра запрос не перезапустит.
> - Куки посетителя во время серверного рендера: `useFetch` пробрасывает их во внутренние `/api`-маршруты, а голый `$fetch` и запросы на сторонние адреса — нет. Заголовки берут через `useRequestHeaders(['cookie'])`.
> - В payload попадает только сериализуемое. Экземпляр класса с методами приедет на клиент без методов.
