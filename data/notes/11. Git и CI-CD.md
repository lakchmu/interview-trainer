## 1. Git: ветки, слияние, перебазирование и откат изменений

> [!tip]+ Коротко (что сказать вслух):
> Git хранит историю как цепочку коммитов-снимков; ветка — это просто указатель на коммит. Изменения проходят три места: рабочая папка, индекс (staging) и репозиторий. Чужую работу подтягивают через `merge` — он сохраняет историю как была и добавляет коммит слияния — или через `rebase`, который переносит свои коммиты поверх свежей ветки и даёт прямую историю. Главное правило: не переписывать то, что уже отправлено в общую ветку. Опубликованный коммит отменяют через `revert`, локальный — через `reset`.

### Три места, где живут изменения

| Место | Что это | Как туда попасть |
| --- | --- | --- |
| рабочая папка | файлы на диске | редактирование |
| индекс (staging) | то, что войдёт в следующий коммит | `git add` |
| репозиторий | история коммитов | `git commit` |
| удалённый репозиторий | общая копия на сервере | `git push` |

| Команда | Что показывает |
| --- | --- |
| `git status` | что изменено и что в индексе |
| `git diff` | изменения в рабочей папке, ещё не в индексе |
| `git diff --staged` | то, что уйдёт в коммит |
| `git log --oneline --graph` | историю с ветвлениями |

- Коммит — снимок всего проекта плюс ссылка на родителя, а не разница с предыдущим.
- Ветка — указатель на коммит, `HEAD` — указатель на текущую ветку. Создать ветку — значит создать ещё один указатель, это мгновенно.

### merge и rebase

```text
до:      main  A───B───C
                    \
         feature     D───E

merge:   main  A───B───C───M      M — коммит слияния, у него два родителя
                    \     /
         feature     D───E

rebase:  main  A───B───C
                        \
         feature         D'──E'   те же изменения, но новые коммиты
```

| | `merge` | `rebase` |
| --- | --- | --- |
| История | как было на самом деле, с развилками | прямая линия |
| Существующие коммиты | не меняются | создаются заново с новыми хешами |
| Конфликты | решаются один раз | могут всплывать на каждом переносимом коммите |
| Безопасно для общей ветки | да | нет |

Золотое правило: **не делать `rebase` ветки, с которой работают другие**. Хеши меняются, и у коллег история расходится с сервером. Свою личную ветку перед открытием запроса на слияние перебазировать нормально.

### fetch, pull и push

| Команда | Что делает |
| --- | --- |
| `git fetch` | скачивает новые коммиты с сервера, свои ветки не трогает |
| `git pull` | `fetch` плюс слияние в текущую ветку |
| `git pull --rebase` | `fetch` плюс перенос своих коммитов поверх скачанных |
| `git push` | отправляет свои коммиты на сервер |
| `git push --force-with-lease` | перезаписывает ветку на сервере, только если там нет чужих новых коммитов |

- Обычный `push` откажет, если на сервере есть коммиты, которых нет у вас: сначала их нужно подтянуть.
- После `rebase` своей ветки обычный `push` тоже откажет — история переписана. Нужен принудительный, и именно `--force-with-lease`, а не `--force`: он не затрёт работу, которую кто-то успел отправить.

### Как отменить изменения

| Что нужно отменить | Команда | Что происходит |
| --- | --- | --- |
| правки в файле, ещё не в индексе | `git restore file` | файл возвращается к последнему коммиту |
| файл в индексе | `git restore --staged file` | убирается из индекса, правки остаются |
| последний коммит, изменения оставить | `git reset --soft HEAD~1` | коммит исчезает, изменения остаются в индексе |
| последний коммит вместе с изменениями | `git reset --hard HEAD~1` | исчезает всё, включая правки в файлах |
| коммит, уже отправленный на сервер | `git revert <хеш>` | появляется новый коммит с обратными изменениями |
| опечатку в последнем коммите | `git commit --amend` | последний коммит пересоздаётся |

| Режим `reset` | Указатель ветки | Индекс | Рабочая папка |
| --- | --- | --- | --- |
| `--soft` | сдвигается | не трогает | не трогает |
| `--mixed` (по умолчанию) | сдвигается | сбрасывает | не трогает |
| `--hard` | сдвигается | сбрасывает | сбрасывает |

`reset` переписывает историю — годится только для неотправленного. `revert` историю дополняет — годится для общего.

### Полезное на каждый день

| Команда | Зачем |
| --- | --- |
| `git stash` и `git stash pop` | спрятать незаконченные правки и вернуть их позже |
| `git cherry-pick <хеш>` | перенести один коммит в текущую ветку — например, исправление в релизную |
| `git rebase -i HEAD~3` | склеить, переименовать или переставить последние коммиты перед ревью |
| `git reflog` | журнал всех положений `HEAD` — спасает «потерянные» коммиты |
| `git bisect` | двоичным поиском найти коммит, который сломал поведение |
| `git blame file` | кто и когда менял каждую строку |

`reflog` — страховка от собственных ошибок: коммит, пропавший после `reset --hard` или неудачного `rebase`, остаётся в журнале ещё около трёх месяцев, и его можно вернуть.

### Конфликт слияния: что это и как решать

Конфликт возникает, когда две ветки изменили одни и те же строки, и Git не может выбрать сам.

```text
<<<<<<< HEAD
const limit = 20
=======
const limit = 50
>>>>>>> feature/pagination
```

1. `git status` показывает файлы с конфликтом.
2. В каждом выбрать нужный вариант или собрать из двух, убрать маркеры.
3. `git add` для исправленных файлов.
4. Завершить: `git commit` после слияния или `git rebase --continue` при перебазировании.

Отказаться от всего — `git merge --abort` или `git rebase --abort`.

Как реже встречаться с конфликтами: короткоживущие ветки, частое подтягивание основной ветки, небольшие запросы на слияние.

### Модели ветвления

| Модель | Как устроена | Кому подходит |
| --- | --- | --- |
| git flow | `main`, `develop`, ветки фич, релизов и срочных исправлений | продукты с версиями и редкими релизами |
| GitHub flow | `main` и короткие ветки фич; слияние — выкладка | веб-сервисы с частой выкладкой |
| trunk-based | все пишут в одну ветку мелкими порциями, незаконченное скрыто флагами | команды с сильным CI и автоматическими проверками |

Чем чаще выкладка, тем короче должны жить ветки. Git flow подробно разобран в конспекте про процессы, раздел 1.

> [!warning]- Подводные камни:
> - `rebase` или `push --force` общей ветки — коллеги получают разошедшуюся историю.
> - `git push --force` вместо `--force-with-lease` — можно молча стереть чужие коммиты.
> - `git reset --hard` без проверки: несохранённые правки в файлах пропадают, и `reflog` их не вернёт — в нём только коммиты.
> - Путать `reset` и `revert`: первый переписывает историю, второй добавляет в неё отмену.
> - `git pull` с привычкой не смотреть, что подтянулось: появляются лишние коммиты слияния.
> - Секреты в коммите. Удалить файл следующим коммитом недостаточно — он остаётся в истории; ключ нужно отзывать.
> - Гигантские коммиты «всё сразу»: их невозможно ни проверить на ревью, ни откатить по частям.

## 2. Основы CI/CD: что такое конвейер и из чего он состоит для фронтенда

> [!tip]+ Коротко (что сказать вслух):
> CI — непрерывная интеграция: каждое изменение автоматически собирается и проверяется, чтобы поломка обнаруживалась через минуты, а не через неделю. CD — непрерывная доставка: проверенная сборка автоматически готовится к выкладке и раскатывается по окружениям; если и в прод она уходит без ручной кнопки, это непрерывное развёртывание. Конвейер — цепочка стадий: установка зависимостей, линтер и проверка типов, тесты, сборка, выкладка. Стадия упала — дальше не идём, запрос на слияние заблокирован.

### CI, доставка и развёртывание

| Термин | Что автоматизировано | Где участвует человек |
| --- | --- | --- |
| Continuous Integration | сборка и проверки на каждое изменение | пишет код и чинит упавшее |
| Continuous Delivery | плюс подготовка релиза и выкладка на тестовые стенды | нажимает кнопку выкладки в прод |
| Continuous Deployment | плюс выкладка в прод | только пишет код |

Зачем это нужно:

- поломка находится сразу и привязана к конкретному небольшому изменению;
- «у меня работает» перестаёт быть аргументом: проверяет чистая машина;
- выкладка становится скучной рутиной, а не событием;
- правила качества одинаковы для всех и не зависят от внимательности ревьюера.

### Стадии конвейера фронтенда

| Стадия | Что запускается | Что ловит |
| --- | --- | --- |
| установка | `npm ci` | расхождение с lock-файлом |
| статический анализ | ESLint, Prettier, `tsc --noEmit` | ошибки типов, стиль, подозрительный код |
| модульные тесты | Vitest, Jest | сломанную логику |
| сборка | `vite build`, `nuxt build` | ошибки сборки, раздувшийся бандл |
| сквозные тесты | Playwright, Cypress | сломанные сценарии пользователя |
| выкладка на стенд | свой адрес для каждой ветки | то, что видно только глазами |
| выкладка в прод | после слияния в основную ветку | — |

Порядок не случаен: **быстрое и дешёвое идёт первым**. Линтер отвечает за секунды, сквозные тесты — за минуты; нет смысла ждать их, если не сошлись типы.

### Как выглядит конфигурация

```yaml
# .gitlab-ci.yml
stages: [check, test, build, deploy]

lint:
  stage: check
  script:
    - npm ci
    - npm run lint
    - npm run typecheck

unit:
  stage: test
  script:
    - npm ci
    - npm test

build:
  stage: build
  script:
    - npm ci
    - npm run build
  artifacts:
    paths: [dist]

deploy:
  stage: deploy
  script: ./deploy.sh dist
  only: [main]
```

| Понятие | Что это |
| --- | --- |
| pipeline (конвейер) | весь прогон целиком |
| stage (стадия) | этап; стадии идут по очереди |
| job (задача) | единица работы; задачи одной стадии идут параллельно |
| runner | машина или контейнер, где задача выполняется |
| artifact | файлы, которые задача передаёт дальше, — например, папка сборки |
| trigger | что запускает конвейер: push, запрос на слияние, расписание |

В GitHub Actions те же идеи называются иначе: workflow, job, step.

### Что ускоряет конвейер

| Приём | Что даёт |
| --- | --- |
| кэш зависимостей по хешу lock-файла | не скачивать `node_modules` каждый раз |
| параллельные задачи | линтер, типы и тесты идут одновременно |
| запуск только затронутого | в монорепозитории проверяются только изменённые пакеты |
| ранний отказ | упавшая быстрая проверка отменяет медленные |
| деление тестов на части | сквозные тесты идут в несколько потоков |

Правило: разработчик должен узнать о поломке, пока ещё помнит, что менял. Если конвейер идёт дольше 10–15 минут, его начинают обходить.

### npm ci и npm install

| | `npm install` | `npm ci` |
| --- | --- | --- |
| Lock-файл | может обновить | только читает; при расхождении с `package.json` падает |
| `node_modules` | дополняет существующую | удаляет и ставит с нуля |
| Результат | зависит от состояния машины | одинаковый везде |
| Где применять | локальная разработка | конвейер |

Смысл CI — воспроизводимость: одинаковый вход даёт одинаковый результат. Поэтому lock-файл хранят в репозитории, а на конвейере ставят зависимости строго по нему.

### Окружения и переменные

| Окружение | Для чего | Кто смотрит |
| --- | --- | --- |
| локальное | разработка | разработчик |
| стенд ветки (preview) | проверить одну задачу отдельно от остальных | ревьюер, тестировщик, дизайнер |
| staging | копия прода с данными, близкими к настоящим | команда перед релизом |
| production | настоящие пользователи | все |

- Один и тот же собранный артефакт должен проходить по всем окружениям. Пересборка под каждое означает, что в прод уедет не то, что проверяли.
- Отличия между окружениями — в переменных: адрес API, ключи, флаги.
- Секреты хранят в настройках CI, а не в репозитории. Всё, что попало в клиентский бандл, секретом уже не является — его видно в браузере.

### Как выкатывают и как откатывают

| Стратегия | Как работает |
| --- | --- |
| разом | новая версия заменяет старую целиком |
| blue-green | рядом поднимается вторая копия, трафик переключают одним движением; откат — переключить обратно |
| canary | новая версия получает малую долю трафика, по метрикам её расширяют или сворачивают |
| фича-флаги | код в проде, но выключен; включают отдельно от выкладки |

Для фронтенда важно:

- файлы сборки называются с хешем содержимого и кэшируются навсегда; `index.html` не кэшируется — он и указывает, какую версию грузить;
- старые файлы какое-то время держат на сервере: у человека с открытой вкладкой старый `index.html`, и ленивый чанк ему нужен прежний;
- откат — это переключение `index.html` на прошлую сборку, а не срочная правка кода.

> [!warning]- Подводные камни:
> - `npm install` на конвейере вместо `npm ci` — сборки перестают быть воспроизводимыми.
> - Lock-файл не в репозитории.
> - Нестабильные тесты, которые «иногда падают»: команда привыкает перезапускать и перестаёт верить красному.
> - Секрет в переменной, попадающей в клиентский бандл.
> - Пересборка под каждое окружение вместо продвижения одного артефакта.
> - Удалить старые чанки сразу после выкладки — открытые вкладки сломаются на ленивой загрузке.
> - Проверки есть, но не блокируют слияние: красный конвейер, который можно обойти, никто не чинит.
